# Learning journal 2026-11-25

### 2026-11-25: Results and lifecycle — Keep peak memory flat in row-building fast paths: stream per-row values, chunk numpy tolist
**Context:** In PR #1078, `_convert_columnar_table` first collected every per-row value list and only then called `_create_rows`. A reviewer flagged the extra peak memory: 107 MB against 88 MB on main for a 200k x 4 table. Separately, walking a numpy object array one row at a time created a view per row, which cost more than the Row construction being removed. Calling `tolist()` on 1024-row chunks fixed the speed without raising peak memory. Calling `tolist()` on the whole array raised peak memory by about 14%.
**Rule:** When optimizing result-row conversion, pass a generator of per-row values instead of a materialized list, convert numpy object arrays with `tolist()` in bounded chunks instead of row-by-row views or one full `tolist()`, and report peak traced memory against main alongside timings.

### 2026-11-25: Results and lifecycle — Prove fast-path object construction is equivalent to the public factory
**Context:** PR #1078 added `_create_rows`, which builds `Row` objects directly with `tuple.__new__` and a `__dict__` write, skipping `Row.__call__`, `__new__` and `__setattr__`. Its tests compare the result with `fields(*values)` for tuple, list, numpy, generator, short and empty inputs. They check type, value types, that `__fields__` is the same object, repr, asDict, attribute and key access, pickle bytes, that rows stay read-only, the exact ValueError message, and rows on both sides of the 1024-row chunk boundaries.
**Rule:** When a performance fast path bypasses a class's normal constructor, test it against the original factory across every input shape for type, repr, equality, pickle bytes, field identity, immutability, exact error messages and chunk-boundary row counts.
